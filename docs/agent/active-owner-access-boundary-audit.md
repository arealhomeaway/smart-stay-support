Static repository audit updated through migrations 43–45 (time writes, invitation redemption and responsibility assignments). No backend inspection or shared migration was performed. The completed scope below describes repository code and unapplied migration behavior, not authenticated acceptance evidence.

## Completed Ticket boundary

- `read_owner_tickets` returns a fixed structural projection: IDs/reference, allowlisted category/priority/status, dates and participation flags. It does not return raw title, description, guest details, credentials, internal notes or unrestricted financial columns. All Tickets at eligible Properties remain represented, including Tickets without Work Orders and archived Tickets retained as history.
- Its private current-Property helper checks the signed-in program account, canonical active Owner, included/unarchived enrollment, matching current Property Owner, Property/program demo alignment, and unarchived Property/program. Demo preview requires an explicit preview request from an administrator. Filters are bounded to 100 Property IDs per call; the TypeScript loader pages every result.
- Migration 41 removes `"Owners read tickets at their home"` and `"Owners open matters at their own home"`. The remaining raw Ticket SELECT/UPDATE vendor paths require an actual vendor role as well as assignment. The shared `private.is_assigned_vendor` fix also covers vendor Ticket activity/checklist policies. UPDATE's `WITH CHECK` tests the proposed row's vendor assignment directly; staff authorization and the demo-write guard remain.
- `create_owner_matter` validates and locks the caller's active program, active canonical Owner, current Property and eligible post-closing enrollment. Fixed operational values prevent owner input from assigning staff/vendors or choosing internal state. Ticket creation, existing automatic-opportunity triggers and the program event commit together; the caller receives only ID/reference. The writer uses `active_task`, which satisfies the existing database record-type constraint.
- Migration 43 supersedes migration 41 logging with a checked definer transaction. It requires the exact opportunity Ticket link, validates the Ticket/current canonical Property under locks, and returns only the entry ID. The owner receives no raw Ticket read permission.
- `loadOwnerTicketProjection` and `createOwnerMatter` use these RPCs. Existing reviewed narrative/authority/actual-cost RPCs remain responsible for their respective owner-safe content. Attachment record lookup uses the verified viewer: owners receive a neutral Ticket reference, while staff retain full labels. All four attachment record-lookup callers pass the viewer; other attachment responses do not return Ticket labels.

Review corrections incorporated into migration 41 include archived enrollment/Property rejection and preservation of the new-row vendor assignment check. Attachment-focused validation passed 22 tests with 51 assertions and focused lint. Full migration/build/authorization results are recorded in the current validation report; this document does not infer a live schema from local tests.

## Time write and account-link boundaries completed locally

Migration 43 removes raw owner entry/link INSERT and supervisor review UPDATE policies. Logging, owner resubmission, staff correction and versioned staff review share program-first NOWAIT locks and explicit lifecycle checks. New time requires an active/target-reached program, canonical active Owner, confirmed current eligible enrollment, an available opportunity (including returned/answered review), actual owner-only account role, valid dates/phase/actual duration, exact Ticket and Property context, and explicit attestation. Program-wide entries may retain zero Property links but still require a post-closing home; shared minutes are stored once. Property/opportunity/role rows are locked. Logging activity timestamps, entries, links and history commit together.

Corrections and review may operate while paused, but completed/archived programs reject them. Corrections preserve original date, Ticket/opportunity, reviewed revision/snapshot, evidence and historical Property links even after enrollment removal; they append one successor and never overwrite the original. Staff review requires the browser-displayed UUID version, rejects superseded entries, and commits review metadata, program event and audit together. Entry core data/deletion, link mutation/deletion and protected time history are guarded. The migration fails before policy removal if the four time writers have different or application-role owners. Trust is in their common privileged database role, not an exact function call stack; other definers using that role still require audit.

The review dialog retains the entry/version/decision/note through background refresh and requires explicit rereview. Logging captures the opportunity phase alongside its exact reviewed narrative. After confirmed logging/correction, no fallible aggregate or badge follow-up can turn a committed receipt into a failed save. Badge evaluation remains a separate hub-load concern and still needs the broader recovery/permission audit.

Migration 44 makes code redemption one service-only transaction: current verified recipient account, canonical active Owner/current post-closing Property enrollment, real program, nonconflicting roles, account linkage, owner role, invite claim, internal immutable receipt and owner-linked history. It preserves the clock and canonical identity, rejects competing/partial linkage, and permits only intact retries. Explicit invite recipient email verifies a code; it never selects or creates an Owner. Missing recipient or canonical identity requires explicit staff reconciliation. Direct authenticated account-link and claim/receipt mutations are blocked. Trusted service maintenance remains privileged and must be audited independently; no real accounts or invitations were changed.

Migration 45 protects project responsibility assignment and the Onboarding Director/Operations Director/Operations supervisor seats and coverage. Ordinary PMs cannot appoint themselves Director through direct project writes or elevated coverage actions. Only platform administrators or the protected Onboarding Director may change project responsibilities; sensitive seats/cover require platform administrators. New ordinary staff projects assign that caller as PM and use the protected Director seat. The migration creates only the missing seat definition, never a person's assignment. Sensitive-seat staff invitation redemption leaves explicit administrator assignment pending. The separate review/handoff gate implementation remains incomplete below.

- `"Signed-in users append program history"` still permits account-linked event INSERT. Response, time and invitation receipt kinds now have guards; other event kinds can still supply misleading history outside their domain actions.
- `"Owners decide their own pending approvals"` leaves a raw UPDATE path. Pending/addressed ownership plus legacy Property visibility does not enforce allowed columns or the atomic Work Order cost/decision/receipt workflow.

- Program canonical identity/later lifecycle, opportunity creation/publication, approval preparation/decision, scheduling and other legacy supervisor/service writers still need a complete shared lock and authorization audit. Account-role additions and all current-role revocation paths must follow the intended lock contract; existing-row locks alone do not prove every concurrent grant path safe.
- Raw Program/Property/review/history/notification/document reads above still use broader account-linked helpers. In particular, tightening the time writer's owner role does not establish owner-role revocation for those reads or the Ticket reader.
- Handoff readiness inputs, stage/task changes, direct handoff status/review history, gate-specific Director authorization and PM/Director/readiness/Operations UI alignment remain implementation work. Protected assignments are a prerequisite, not completion of that chain.

The isolated SQL fixtures cover rejected operations, stale versions and forced rollback. They do not prove deployed RLS/default privileges, every other trusted writer, or simultaneous transactions on separate database connections.
