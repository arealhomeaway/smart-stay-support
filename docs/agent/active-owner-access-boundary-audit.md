# Active Owner access boundary — September 16

Repository audit through migrations 46–48. This describes branch-local code and isolated checks; no shared backend was inspected or migrated. **MORE IMPLEMENTATION REQUIRED.** Authenticated acceptance is not yet the only major gate.

## Implemented local boundaries

- **Tickets (41, 46, 48):** owner reads use fixed structural, reviewed-narrative and financial projections. Raw owner Ticket SELECT/INSERT is removed. Actual vendor role plus assignment is required for raw vendor Ticket/activity/checklist access. Current canonical Owner, current included/nonarchived same-mode Property/enrollment, active account and owner-only role are required for structural/latest narrative reads. Explicit administrator preview is separate. Automatic opportunities preserve canonical Ticket/Property/program links and include review-only work. Owner matter creation uses fixed operational values and an atomic Ticket/opportunity/history transaction.
- **Program/Property (46):** raw owner Program and Property SELECT policies are removed. Safe RPCs explicitly list fields, use the canonical Owner's name/email, exclude private program notes/closeout payloads and Property credentials, and reject forged actor/preview, inactive/deleted/banned accounts, revoked/conflicting roles, transferred/archived/excluded/mixed-mode Properties. Service callers must supply the verified actor. Removed enrollment retains its historical IDs/dates without current home facts. Completed program history remains readable; archived programs are denied. Preferences use a narrow locked transaction and cannot change other program fields. Hub, aggregate, reports, approval Property labels and elevated Property Hub use these projections; staff readers retain their existing internal access.
- **Time, corrections and account linkage (43–44):** checked transactions enforce actual owner-only role, current canonical post-closing scope, explicit attestation, dates/phase/opportunity/Ticket/revision, lifecycle and version checks. Corrections preserve original evidence, dates, Property/Ticket/activity/revision links, including after removal. Entry/link/history immutability and one-successor safeguards apply; staff review and its audit commit together. Verified-recipient invitation redemption atomically binds the existing canonical Owner/program, account role, claim, receipt and history without resetting the clock or inferring an Owner from email.
- **Reviewed intent (48):** immutable Ticket updates include the explicit owner request and WHY. Canonical pending approval takes precedence; other categories come from reviewed intent and legacy records retain authority/review fallback. Response/time/correction snapshots preserve the exact intent and narrative. A participation response does not certify payment, completed work or spending approval. Publishing a later revision does not edit an earlier receipt.
- **Elevated files/Property Hub:** all owner paths recheck current canonical scope with the verified viewer and bound document/entity/Property/demo context. Owner responses omit staff notes, profile-email fallbacks, raw task/blocker narratives and audit labels. Upload-key retries are bound to actor/entity/Property/mode/file/path; requested-file completion checks the intended request. Failed completion retains its attempt instead of deleting bytes. Signed upload tokens and the matching client disallow object overwrite. These endpoint fixes do not close the independent document policies or historical sharing-recipient issue below.
- **Responsibility and handoff (45–47):** protected Director/Operations seats and assignment controls prevent PM self-promotion. PM submission remains separate from Director review, including when one person holds both roles. Readiness review, acceptance and Live use their respective protected roles, with explicit administrator recovery. Stage/handoff transactions retain reviewed snapshots, recheck current inputs and reject stale or forged transitions; task/scope/evidence changes require renewed review. Direct handoff/review writes are constrained. Full-schema and simultaneous-session acceptance remain required.

## Exact remaining privacy and write paths

The detailed table/policy/caller inventory is [the owner read-boundary follow-up](owner-read-boundary-follow-up.md). These are implementation defects, not merely missing browser evidence:

1. **Reviews and history:** `"Owners read their own reviews"` still uses account-only `private.owns_program` and exposes `staff_context` and legacy content. `"Owners read their program history"` permits arbitrary detail/prior/new values. Replace owner reads with current-opportunity and separately retained immutable-history projections before removing raw access. Never substitute a latest narrative for a recorded revision.
2. **Enrollment/review/time links, badges and notifications:** independent account-linked policies still need canonical account/role checks and explicit safe fields. `"Owners read their own alerts"` exposes legacy raw notification content despite sanitized hub text. Preserve historical participation while denying current operational access after transfer/removal.
3. **Approvals:** owner SELECT is not restricted to the actual owner-addressed safe request. `approvals_update_decider` and `"Owners decide their own pending approvals"` permit direct row UPDATE beyond the versioned atomic response contract, including mutable amount/entity/Property/status. Close the direct path and preserve legitimate staff/recipient decisions through authorized domain actions.
4. **Documents:** `documents_read_owner_shared`/`private.owner_can_see_property` still permit raw metadata without the new current canonical checks; `documents_update_sup` permits uploader metadata mutation. Sharing flags have no canonical Owner/program recipient binding. A new Owner can inherit a former Owner's shared files/request slots on the same Property. Future shares/requests must preserve an explicit canonical recipient, and legacy unbound shares need review or denial rather than recipient inference from current ownership. Do not erase file/history records.
5. **Upload transaction and signed capabilities:** file completion, original requested-file claim, history and token issuance are not one transaction. Conditional updates and non-overwriting tokens improve behavior but do not prove simultaneous completion or revocation of already-issued URLs. Real storage acceptance, retry recovery and retained failed-object handling remain unverified; no external storage was touched.
6. **Other direct/privileged writers:** account-linked nonprotected program events can still fabricate history; later program identity/lifecycle, enrollment/removal/reassignment, opportunity creation/publication, financial/approval preparation, scheduling and trusted maintenance writers need the shared authorization/lock protocol. Existing row locks do not prove every concurrent role insertion/revocation path safe. Exact closure/report invalidation must cover all relevant writers.

## Validation limits and next implementation

The local tests exercise denied operations, paging, stale versions, forced rollback, immutable snapshots and actual role fixtures. They do not prove deployed default privileges, full production-schema policies, independent transactions on separate database connections, real storage, authenticated desktop/390px interaction or every trusted definer.

Continue with safe child-table/approval/document reads and direct writers, canonical sharing recipients, revised linked approvals, remaining lifecycle/closeout/identity writers, then module/Director queue and report/badge/90-day consistency. Exactly **100.0 counted hours qualifies**; the 105-hour operating benchmark does not alter that locked target.
