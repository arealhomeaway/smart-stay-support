# src/lib rules
- Help ticket bulk updates use one caller-authenticated transaction with per-ticket events and replay receipts; notifications reuse the single-update recipient and email path, claimed once per batch and grouped by submitter. Why: all-or-nothing history and no duplicate submitter emails.
- Outbound email must pass email-safety.server.ts plus the database email_delivery_allowed guard before provider access; email-job.server.ts records synchronous pass results and stops on audit/errors. Why: demo/test sends fail closed and timed-out calls remain auditable.
- Vendor sourcing/dispatch: candidates, append-only contact attempts and visits live in work_order_vendor_candidates/_contact_attempts/_visits; rules only in src/lib/vendor-sourcing.ts (authority via evaluateAuthority); DB trigger wo_authorization_snapshot marks approval stale on scope/amount change and gates Breezeway handoff; one request key per Work Order; demo handoffs simulated. Why: acceptance, authorization, dispatch, completion stay separate facts, no duplicate external tasks.
- Vendor execution: vendor changes only via Work Order candidate acceptance; Telegram tri-state (unknown until staff confirm); Breezeway handoff saved as uncertain before the call and never retried until reconciled; estimates never count as invoiced or pass Finance review. Why: no silent vendor swaps, no duplicate external tasks.

- Property Activity files: uploaded via the shared attachment path as property-level Operations documents, linked by `property_activity_log.attachment_document_ids`; insurance labels only from `insuranceRiskLabel` in `src/lib/work-entry.ts`. Why: one upload path, one label rule.
- Review identity: `guest_feedback.reviewer_display_name` (review source) never overwritten by `reservation_guest_name` (OwnerRez booking, filled by `enrichReviewReservations`). Why: public reviewer ≠ booking guest.
- Finance expenses: one `expenses` record per invoice/receipt (amount stored only there), linked via `expense_links`; history append-only in `expense_events`; Finance authority enforced by DB trigger `guard_expense_write` using `finance_lead`/`accounting` functional seats; readiness rules only in `src/lib/expenses.ts`; Finance files are `documents` with entity_type `expense`, internal-only (DB guard). `financial_requests` stays onboarding-only. Why: one rule, no duplicated amounts, no owner access.
- Finance expenses are created only by an explicit save with a payee or home plus an amount or reason (DB `guard_expense_extra`); accidental records are voided only via audited `archive_expense` and archived rows are excluded from queues/totals; expense authorization evidence reuses `evaluateAuthority` from `src/lib/work-orders.ts`; leadership decisions route only to `is_director` holders. Why: no blank records, one authority ladder, no undeliverable decisions.
- Active Owner setup uses enrollActiveOwner and durable active_owner_enrollment_step checkpoints over existing canonical RPCs; welcome queueing stays at the final checkpoint and delivery only after wording approval. Why: one setup path, retry receipts and no duplicate or unreviewed welcomes.
- Active Owner logging eligibility is enforced by private.lock_owner_time_program and owner_hours_eligibility; the UI mirror opens at enrollment while retaining paused/closed and identity checks, contingent on approved pending SQL. Why: one authority, no browser-only bypass.
- Vendor email dispatch: "Email work order to vendor" (vendor-email.ts rules, vendor-email.functions.ts send) is shown on every open Work Order but enabled only when Breezeway cannot reach the accepted vendor (disabled with the reason otherwise), sends through the shared staff email path, records a `sent_to_vendor_email` work_order_events row, and never calls Breezeway. Staff-composed Breezeway sends require a date and an assignee via `dispatchBasicsProblem` in the server validator. Why: no undated/unassigned external tasks and one email path.
- Onboarding Task homeowner email: "Email homeowner" in TaskDrawer reuses EmailComposer (context onboarding_task); recipient split, CC defaults, template suggestion and merge keys live only in src/lib/task-email.ts; after a real send, task-email.server.ts records onboarding_project_events (homeowner_emailed) and property_activity_log. Why: one email path, no internal data in merges.
- OwnerRez reviews import nightly via `runNightlyReviewSync` (review-sync.server.ts) on the existing five-minute job, gated by pure `nightlyReviewSyncDue` to the 2 a.m. Central hour; each run is an `integration_events` row (system `ownerrez_reviews`) shown on Integrations. Why: no new cron, visible failures, one review per OwnerRez ID.
- One claim per ticket is enforced by unique index `claims_one_per_ticket`; claim creators reopen the existing claim on a duplicate error. Why: double clicks never create two claims.
- Survey Reviews are created only by DB trigger `guest_survey_response_creates_review` (event_key `survey:<feedback_id>`); Maintenance Reviews are one `routine_controls` row per Breezeway work order (`bz_maint:<id>`), and only a completed review counts as approved, never Breezeway Finished; nothing writes back to Breezeway. Why: one task per event, no retroactive work, vendor completion is not team review.
- Work order calendar merges Resolve and synced Breezeway work via `src/lib/work-order-calendar-sources.ts`; a Breezeway task linked by `breezeway_task_ref` shows once as the Resolve Work Order. Ticket section visibility lives only in `src/lib/ticket-sections.ts` and never changes business rules. Why: one display rule, no duplicates.
- Guest Touch Bases are created only by `runGuestTouchBaseSync` (guest-touch-base.server.ts) on the five-minute job, at most hourly, one `routine_controls` row per OwnerRez booking (`touchbase:<booking id>`); rules (4+ nights, day 2 Central, start date, cancellation close) live only in `src/lib/guest-touch-base.ts`; reads OwnerRez only and never contacts guests. Why: one task per reservation, no retroactive or duplicate work.
- Team & coverage schedule edits are planned only by pure `src/lib/team-schedule.ts` and written through audited coverage-admin server functions; person changes for every week go through `setSeatHolder`. On call = weekday pattern (app_settings `oncall_weekday_pattern`) plus dated oncall_roster rows that always win, resolved by `oncallForNight`, mirrored by DB `oncall_user_for_night`; pickers, grid rows and test accounts come from settings, never hardcoded names. Why: screen, Breezeway routing and app ticket routing read the same rows and never disagree.
- Notion ticket import runs only from the Admin page via `notion-import.functions.ts` in small resumable batches; group/assignee/team/claim/home rules live only in `src/lib/notion-import/mapping.ts` (Team Queue group reuses `importTeamGroup`), run state, stop/resume/crash, duplicate-plan and backoff rules only in `src/lib/notion-import/runner.ts`, saved in app_settings `notion_import_runner` after every batch and logged per batch to integration_events; writes go through caller-authenticated import RPCs that quiet triggers; tickets reopened or taken are never rewritten; older open imports are held as `backlog_review`, which display treats as older. Why: reruns key on page ID, a stop or crash loses nothing, imports start no clocks.
- Refund and compensation authority: limits only in `RECOVERY_POLICY` (src/lib/recovery-policy.ts), levels only from `evaluateAuthority` (src/lib/guest-recovery.ts); the pending DB guard `recovery_required_authority` repeats them and `refund-authority-sql.test.ts` fails on drift. Why: screen and database can never disagree on who approves.
- Removing people: staff are deleted only via DB remove_staff_user as a kept profile tombstone (removed_at, "(former)" via formerName) after open work is reassigned; homeowners/vendors are archived via set_account_archived; logins are banned, never deleted, and profiles refuse deletes. Why: no cascade can erase hours, approvals, documents or audit history.
- Refund Approve/Decline go only through DB `decide_recovery_approval` (role checked in the database, reason required, in-app notice); trigger `guard_recovery_decision_trg` refuses direct status writes; screen visibility from `canDecideApproval`. Why: approver authority cannot be bypassed from the browser.
- Evidence checklists for new refunds/credits and claims are created only by `createEvidenceSlotsFn` (evidence-slots.functions.ts), which checks the caller created the record and removes it if the checklist fails; staff have no direct insert right on evidence_requirements. Why: no half-saved refunds or claims.
- Ticket layout (tracker, Do this now, Make it right, collapsed Details) is display-only; step mapping, due line and refund chip live only in src/lib/ticket-cleanup.ts and Approve/Decline only in RecoveryDecisionBox. Why: the page can change without touching routing, SLA or approval rules.
- Supervisor check (`/supervisor-check`) is read-only and groups tickets only via pure `src/lib/supervisor-check.ts`; it links to items and never writes. Why: one daily review surface beside Oversight, no second workflow.
- Nightly backup uses only the in-app SharePoint integration key of resolve.integration (getServiceSharePointConnectionKey); rules live in pure src/lib/nightly-backup.ts, runs log to backup_runs, retention deletes only folders recorded there, and the trigger route requires the database-held token checked by backup_verify_cron_token (no app secret). Why: no personal sign-in, no deleting folders it did not create, no publishable-key access to a writing job.
- Ticket dispatch next step comes only from pure dispatchNextStep (src/lib/dispatch-next-step.ts): vendor, acceptance, authorization, appointment, then Breezeway or email per the server email rule; actions reuse existing writes and server functions. Why: PCs always see the one missing piece, server checks unchanged.
- Active Owner cards show files staff shared (owner_shared) on their linked onboarding step only via `cardFilesByReview` in owner-onboarding.server.ts, and only once unlocked. Why: one file-sharing path, no files before a card opens.
- Marketing photos: folder path, photo cards and caps only in `src/lib/marketing-photos.ts`; owners never get SharePoint access, downloads go through a logged single-use link and the pull-driven `streamPhotoZip` (no full zip in memory). Why: owner-only access, auditable downloads, bounded memory.
- Imported Notion tickets: their state (recent open, older open, historical, live) comes only from `notionTicketState` in `src/lib/notion-ticket-display.ts`; queues, unclaimed count, Needs you now, Oversight and rates filter with `withoutQuietNotion`; open ticket totals (home page, homes list, Hub, map) use `countsInOpenTotal`, which still counts recent open imports; a recent import assigned to someone shows only in their My work Active via `isMyRecentImport`, with no clock; they become live only through caller-authenticated `reopen_notion_ticket` with fresh clocks. Home sections use `src/lib/home-work.ts`. Why: one rule keeps imports quiet everywhere and credits only work after reopening.
- Routine checks: the Record routine work panel (`src/components/routines/RecordRoutinePanel.tsx`) is the one place open checks are recorded; live/retired checks, steps and answer rules live only in `src/lib/record-routine.ts`; saves go through caller-authenticated `record_routine_check`, which alone maps a found issue to its work type and links the ticket. Top bar "Record work" and "Record routine work" visibility comes only from `topBarWorkActions` in `src/lib/shell-nav.ts`. Why: one save path, no lost issues, no duplicate tickets, and the two buttons never disagree.
- Scorecard capture: facts go only through role-checked DB functions into add-only `scorecard_records` (server time, `about_imported_ticket` flag, `scorecard_records_countable` view); browser rules and wording live only in `src/lib/scorecard-capture.ts`; queue sweeps are logged on page open by `QueueOpenLogger`, never a button; tickets are archived via `archive_ticket`/`restore_ticket`, never deleted. Why: history nobody can edit, one filter for exclusions.
- Closed-ticket Reopen (any staff who work tickets, not onboarding) goes only through DB `reopen_ticket` via `ticket-reopen.functions.ts` (fresh clocks from `reopenClocks`, caller assigned, one history line, no direct-update fallback); quiet Notion imports keep `reopen_notion_ticket`. Urgency display names live only in `URGENCY_NAMES` (src/lib/tickets.ts). Handoff Accept/Decline saves the ticket first and records the handoff only when the ticket row changed (`settleHandoff`). Why: one reopen rule, one wording source, no false handoff success.
- New coordinator work is routed only by DB `coordinator_for` over `coordinators_on_shift` (saved schedule, overrides, lunch columns on coverage_shifts, non-Waiting load); `ticket_route_at` is the whole ticket ladder used by `auto_assign_ticket` and `routing_dry_run`; `direct_booking_on_shift` reuses `coordinators_on_shift` and returns nobody inside the after hours window; overnight requests are marked `leads.overnight_until` by a BEFORE INSERT trigger, shown in the Team Queue from that mark, alerted once by `release_overnight_direct_bookings` on the existing 20 second job, and timed from `clockStart` in direct-bookings.ts; quiet Notion imports never count in load; Home shows unstarted Direct Bookings to the people their alert rows name plus anyone `direct_booking_eligible_now` (`homeStartIds`, `homeDirectBookings`). Breezeway keeps its own order, only plain notes from `COORDINATOR_ROLE_LABELS`. Staged in docs/pending/routing-by-time and routing-tweaks. Why: one routing rule for tickets, alerts and Home.
- Direct Bookings rules (rent discount by referral source record id, status chips, views, tiles, follow-up due, reply email format) live only in `src/lib/direct-bookings.ts`; server functions take no Cc from the screen (role holders of the Operations Supervisor and Director of Operations, never a COO holder) and refuse Active Owner homes before any send, repeated by the staged DB functions in docs/pending/direct-bookings-fix/. Why: screen, email and database cannot disagree on price, copies or which homes can be offered.
- Team-role permissions (Operations Supervisor held or covering, Project Manager, Utilities) reach the app only through `loadTeamRoleSeats` (access-seats.ts) into `AccessSeats`; view-only access uses separate capabilities (`work_orders_view`, `finance_view`, `owner_insight_view`, `team_schedule_view`, `playbooks_view`) and never the working ones; `__tests__/access-matrix.test.ts` records who opens which page and does its main action and must change only with an approved permission change. Why: no new account types and no silent widening.
- Screen wording is guarded by `src/lib/__tests__/screen-words.test.ts`, which reads every string and JSX text in src (not comments, tests or identifier-like strings) for banned words and staff first names; text needing separate approval sits in its FROZEN list, whose counts may only go down. Homeowner escalation contacts in `arha-contacts.ts` are roles with the shared company phone and email. Why: names and banned words cannot creep back onto screens.
- Vendors page access lives only in `vendorPageAccess` (src/lib/vendor-page-views.ts): everyone who opens Vendors sees every tab their edit right allows and every record; `vendor_admin` edits companies, service areas and home coverage; `vendor_leadership` alone changes status, Gold Standard, compliance, screening, documents, logins, imports, columns and saved views, which others see read only, never hidden. Why: onboarding reads the full vendor database without taking leadership decisions.
- Playbook and SOP editing (save, approve or publish, archive, review notes, SOP upload) uses one rule: `canEditPlaybooks` in src/lib/playbook-editing.ts mirrored by DB `can_save_playbooks` (Admin, both Directors, Operations Supervisor holder or cover); everyone else reads. Ticket checklist publishing (`publish_ticket_checklist`) and the Ticket checklists screen use the same rule; the page opens for every staff account. Why: screens and database agree and viewers never see edit controls.
- Before building any request, read docs/decision-register.md. If the request conflicts with a line in it, do not build that part; say which line (for example A9 or D6) and why. Where the register and old code disagree, the register wins. Never change anything the request does not name.
- Repair approval policy versions: the current policy lives in app_settings `maintenance_authority_policy` with older versions under `previousVersions`; each Work Order and its linked Finance record are decided by the version stamped on the Work Order (`policyForVersion` in src/lib/maintenance-policy.ts, mirrored by DB `private.expense_authorization_detail`); onboarding cost requests keep their own `onboarding_authority_policy`. Why: a policy change never re-decides existing work, and screen and database read one ladder.
