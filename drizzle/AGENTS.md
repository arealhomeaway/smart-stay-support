# STR cleaner safeguard (database rules)
- Nightly cron `str-cleaner-time-nightly`: 07:00 UTC primary; 07:30/08:00/08:30 resume unfinished runs, no-ops once complete. Why: resumable, no duplicates.
- Safeguard state only in `private.cleaner_safeguard_state`/`_eval`; UI/RPCs never recompute. Why: one authoritative rule.
- Dispatch = Resolve check-before-assign (`cleaner_record_dispatch`); Breezeway-native assignments evaluated/alerted, never undone. Why: Breezeway writes allowlisted.
- Overrides single-clean, append-only (`cleaner_safeguard_overrides`), `private.is_director` only. Why: permanent audit.
- Re-evaluation via deferred trigger on `cleaner_exposure_ledger`; alert only on escalation/new inversion. Why: no duplicate alerts.
- `cleaner_workers` = person directory; other sources write append-only `property_work_records`; `property_person_activity` consolidates. Cleaner ledger is the only safeguard input. Why: extensible.
- Departure Review: created only by DB `create_departure_review_from_clean` (Finished/Approved/Closed housekeeping clean + ended reservation, unique event_key); separate `cleaning_reviews` record; rules in `src/lib/departure-review.ts`; real homes gated by app_settings `departure_review_live_homes`. Why: one trigger, no duplicates, legacy routine generator retired.
- Departure clean → reservation matching: pure rules in `src/lib/departure-matching.ts` (configurable clean types via app_settings `departure_clean_task_types`); saved states in `departure_clean_matches` (manual links never overwritten, one Matched clean per reservation) with append-only `departure_clean_match_events`; review trigger reads snapshot or Matched record and allows one review per reservation. Why: never guess a reservation, no duplicate reviews.
- Claims: stage gates (submission proof, decision evidence, reasons, nonrecovery) enforced by DB `guard_claim_workflow`; received money only via append-only Finance-seat `expense_recoveries` (claim_id, corrections as reversing rows, capped per linked expense) synced to `claims.recovered_amount`; waivers via `request_claim_waiver`/`decide_claim_waiver` (supervisors, in-app). Why: one ledger, approval ≠ receipt.
- Claim waivers routed by `private.route_claim_waiver` (Pod supervisor when modelled → ops_supervisor seat → director_ops on self-conflict → visible exception), never broadcast; approval only stops recovery — closure with a shortfall needs `record_claim_finance_treatment` (+ leadership decision if flagged). Demo claim alerts go only through `notify_staff_isolated` to synthetic accounts listed in app_settings `demo_notification_recipients`; retraction via audited `retract_demo_notifications`. Why: no real-staff demo alerts, approval ≠ accounting.
- Statement Readiness: `statement_dispositions` (one current per expense, append-only supersede) via `record_statement_disposition` (Finance seats); `statement_reconciliations` sign-off via `confirm_statement_reconciliation` (Finance Lead only, manual source ref, snapshot); triggers on expenses/recoveries/dispositions mark sign-offs invalidated, never overwritten. Labels/blockers in `src/lib/statement-readiness.ts`. Never posts to OwnerRez/QuickBooks. Why: one disposition per expense, no double counting, preserved history.
- Owner completion reviews: append-only `owner_completion_reviews` via `record_owner_completion_review` (staff follow-through only; never changes owner completion, hours or handoff); queue via `owner_completions_for_review`, forward-only from app_settings `owner_completion_review_start`; owner feedback is a staff `owner_request_messages` row + in-app owner alert (no email). Why: no duplicate Tasks, no backfill, internal notes never owner-visible.
- Demo lens for non-admins only via `private.is_demo_finance_tester` (audited app_settings `demo_finance_accounts` + synthetic email + Finance seat), managed by admin `set_demo_finance_access`; never grants View As or seed/reset. Why: Finance QA without admin rights.
- Statement sign-off refuses included expenses whose Finance review was reopened. Why: changed expenses never count as ready.
- Finance review evidence gate: completing review requires `private.expense_documentation_ok` (stored, non-archived designated invoice + required facts/photos); changing designated invoice/required-photo evidence on a reviewed expense needs a reason and reopens review via `expense_evidence_reopen` (prior reviewer kept in `expense_events`); archiving a designated file removes it through the same path. Undesignated attachments and notes never reopen. Why: a review never covers evidence supplied afterward.
- Expense authorization gate: Finance review and Include require `private.expense_authorization_detail` ok (vendor_service only); thresholds only from app_settings `maintenance_authority_policy` (fails closed; app loads it via `applyStoredMaintenancePolicy`); supervisor-band approval only by `private.can_approve_spending` (ops_supervisor/director_ops seat, cover or seat member — never admin/manager/Finance alone), stamped by `wo_supervisor_decision_guard`; owner band needs owner approvals row; notes never count; the approver can never complete that expense's Finance review. Why: one authority rule, separation of duties.
- Demo lens for named staff: `set_demo_staff_access` (admin, audited, revocable) lists users in app_settings `demo_staff_accounts`; grants only the Demo view via `my_demo_access`, existing seats govern actions. Why: staff acceptance without admin rights.
- Active Owner hours: an owner's homes closing in the same calendar year form one automatic participation group; every entry dated in that year (home-tagged, General or pre-closing) counts once (`participationYearTotals`, `inParticipationWindow`); years stay separate; DB `log_owner_time_entry` accepts dates in a confirmed-closing year; no DFY/Day-One/approval gate; demo programs accept entries only from synthetic owners passing `demo_owner_link_ok`. Why: DFY grouping guidance, one counting rule, no double count.
- Actual closing corrections only via `correct_actual_closing` (Manager role or director_ops/director_onboarding seat; admin alone refused): updates property + included enrollments, recomputes program clock under `app.closing_correction`, appends program event + audit; planned closing untouched, entries never deleted. Why: one corrected date everywhere, full history.
- Synthetic test accounts (reserved test email domains, `private.is_synthetic_account`) are demo-only via a RESTRICTIVE policy on every RLS table with `is_demo` or `property_id`, plus guards in SECURITY DEFINER readers and a caller-RLS check before file signing. Why: test accounts never touch real records or files, regardless of role or seat.
- Onboarding review steps: settings per template step in `onboarding_step_review_settings` (no row = off), reviews/decisions/history only via caller-authenticated review RPCs; completion and handoff are held by DB guard triggers; reviewers resolve cover, then Project Team/seat, then Onboarding Director; alerts in-app only. Why: one rule for every completion path, defaults change nothing.
- Active Owner plan engine: per-home plan cards are written only by caller-authenticated ao_* RPCs (applied as migrations 0230-0232 from docs/pending/ao-engine/); unlock runs from the onboarding Task completion trigger, which only reads the Task. Screens reach engine objects only through src/lib/ao-data.ts, which treats missing objects as "Not set up yet" (isMissingDbObject), and the 5-minute job runs ao_process_clocks last via runAoClocksGuarded. Why: one engine path, templates and home plans never modified, code can ship before the database.
- Active Owner card de-duplication: coverage is decided only by private.ao_card_coverage (live linked-Task item or confirmed ao_card_item_map entry) and repeats of a live card are refused by the ao_guard_owner_item BEFORE INSERT trigger on owner_reviews/work_items, bypassed only by a single-use ao_confirm_one_off; suggestion rows never count until confirmed. Why: one guard covers every send and release path.
- Participation report wording comes only from the versioned report_wording_versions record via report_wording_current (fallback FIXED_REPORT_SENTENCES in src/lib/report-v2.ts until applied); entry Logged by/card labels come only from report_entry_labels (engine link, then Admin-approved legacy map, else "Earlier activity") and never touch hour records. Why: one wording rule, labels without changing logged hours.
- Handoff reminders come only from `run_handoff_reminders` (daily job acting in the 8 AM Central hour), once per project, handoff date and reminder in `handoff_reminders`; bulk flag changes save exact prior values in `onboarding_flag_snapshots` for undo. Why: no duplicate reminders, moved dates reschedule, bulk changes stay reversible.
- Active Owner plan start (staged docs/pending/active-owner-fix): a home's program comes only from private.ao_home_program (primary or included home, one live program, else refused); every card outcome comes from private.ao_plan_outcomes, shared by preview, switch, enrollment start, Start plans for enrolled homes and the handoff step, with the operations-card exceptions only in private.ao_ops_card_rule (staged 06); owner Active Owner email is one plan is ready notice plus held card emails folded into one daily email by ao_owner_email_run (ao_owner_email_days caps one per owner per Central day); a Task sent as an owner item completes on send and the conversation lives on owner_request_messages; a demo home matches only a demo program (staged 06), runs the same engine, and every notice it creates is skipped for email and SMS. Why: preview equals result, owners never get an email per card, and demo testing never reaches anyone.
- Admin passes every onboarding and Active Owner role check (staged 06 adds the three missing paths: Mark ready, step review decide and edit); screens show those Admin paths only when DB admin_passes_role_checks answers yes, and every Admin action still records the Admin as actor. Why: one authority rule, no button the database would refuse.
