## Completed Ticket boundary

- `read_owner_tickets` returns a fixed structural projection: IDs/reference, allowlisted category/priority/status, dates and participation flags. It does not return raw title, description, guest details, credentials, internal notes or unrestricted financial columns. All Tickets at eligible Properties remain represented, including Tickets without Work Orders and archived Tickets retained as history.
- Its private current-Property helper checks the signed-in program account, canonical active Owner, included/unarchived enrollment, matching current Property Owner, Property/program demo alignment, and unarchived Property/program. Demo preview requires an explicit preview request from an administrator. Filters are bounded to 100 Property IDs per call; the TypeScript loader pages every result.
- Migration 41 removes `"Owners read tickets at their home"` and `"Owners open matters at their own home"`. The remaining raw Ticket SELECT/UPDATE vendor paths require an actual vendor role as well as assignment. The shared `private.is_assigned_vendor` fix also covers vendor Ticket activity/checklist policies. UPDATE's `WITH CHECK` tests the proposed row's vendor assignment directly; staff authorization and the demo-write guard remain.
- `create_owner_matter` validates and locks the caller's active program, active canonical Owner, current Property and eligible post-closing enrollment. Fixed operational values prevent owner input from assigning staff/vendors or choosing internal state. Ticket creation, existing automatic-opportunity triggers and the program event commit together; the caller receives only ID/reference. The writer uses `active_task`, which satisfies the existing database record-type constraint.
- `log_owner_time_entry` retains invoker security. Its Ticket check now uses the safe reader and requires the exact Ticket linked to the chosen opportunity. This removes its dependency on raw owner Ticket SELECT; it does not close every participation writer or lifecycle race below.
- `loadOwnerTicketProjection` and `createOwnerMatter` use these RPCs. Existing reviewed narrative/authority/actual-cost RPCs remain responsible for their respective owner-safe content. Attachment record lookup uses the verified viewer: owners receive a neutral Ticket reference, while staff retain full labels. All four attachment record-lookup callers pass the viewer; other attachment responses do not return Ticket labels.

Review corrections incorporated into migration 41 include archived enrollment/Property rejection and preservation of the new-row vendor assignment check. Attachment-focused validation passed 22 tests with 51 assertions and focused lint. Full migration/build/authorization results are recorded in the current validation report; this document does not infer a live schema from local tests.

Automatic opportunities exclude raw evidence, impact, outcome, attachment and photo fields; narrative comes from the reviewed Ticket projection. Manual publication fields and their legacy attachments still need a complete publication/authorization review.

## Remaining direct writes and lifecycle/time races

- `"Owners log their own time"` in `20260821043207_2e25ffe3-b9bb-4fcb-be2a-e684bb8cb2da.sql` still permits direct time-entry INSERT using owner/account linkage. The baseline validation trigger checks minute limits and future dates, not the full program/opportunity/current-Property contract. `capture_owner_time_update` supplies stronger checks only when an immutable reviewed revision is supplied; a null revision takes its early return. Raw INSERT must not bypass the atomic logging contract.
- `"Owners link their own entries"` in `20260821143055_492f3645-563a-4b91-ad95-1d0307c54e51.sql` permits direct property-link INSERT based on entry ownership without enforcing that the Property belongs to that opportunity/current enrollment. Corrected historical links must remain durable.
- `"Signed-in users append program history"` in the same migration permits account-linked event INSERT. The response-receipt trigger protects its specific response kinds, but other event kinds can still bypass an atomic domain action or supply misleading history.
- `"Owners decide their own pending approvals"` in `20260828143022_a986f7c7-8d00-481d-9e37-227749d44f32.sql` leaves a direct UPDATE path. It checks pending/addressed ownership and Property visibility, not an allowed-column set or the atomic Work Order cost/decision/receipt transaction.
- `"documents_update_sup"` in `20260821162752_8d5e9682-9b99-4294-893f-0a8253707dc0.sql` permits uploader UPDATE alongside supervisor access. An owner's uploaded document can therefore have a direct metadata writer outside the attachment actions; constrain it without breaking legitimate requested uploads.
- `log_owner_time_entry` reads program, opportunity and enrollment eligibility without locking that context for the whole transaction. Its new Ticket read is a snapshot, not a lifecycle lock. An opportunity closure, Property transfer/exclusion or program closeout can race a time write, particularly without a reviewed revision. The report-version AFTER trigger can acquire the program lock after eligibility was read; it does not revalidate lifecycle state. Non-Ticket opportunities also do not call the new canonical Ticket reader at all.
- Returned-entry resubmission and staff correction retain immutable context and share a correction lock, but their lifecycle contract still needs to cover concurrent closeout and historical-versus-current eligibility explicitly. Do not make retained receipts disappear merely because enrollment ends.
- `redeemOwnerInvite` still performs program linkage, role work and invite redemption as separate elevated requests. The conditional final invite update does not make the earlier account assignment atomic; concurrent redemption/account-link changes require one canonical transaction. This audit does not authorize real account or invite changes.

Migration 42's explicit activation/enrollment locking and preserved program clock are separate work. They do not by themselves close these raw participation writers or serialize every time-entry/response/closeout path.

## Remaining implementation sequence

1. Extend the external-owner boundary to Program and Property; replace aggregate/approval/elevated Property context dependencies before removing raw owner policies. Keep staff paths and historical participation usable.
2. Add explicit review/event/notification/document/asset reads and canonical revocation checks, then remove their independent raw exposure. Review manual publication content separately from internal operational content.
3. Make time entry, property links, approval decisions, account linking and their events callable only through fully validated atomic actions; restrict remaining direct policies accordingly.
4. Serialize program/opportunity/Property eligibility with time writes, corrections, responses and closeout. Test both race outcomes; preserve exact historical evidence and legitimate correction rights.
5. Verify the full schema with actual owner/staff JWTs, two unrelated owners, included/excluded/transferred/archived/demo Properties, genuine and forged vendor assignment, and separate concurrent sessions in an approved isolated environment.

Do not globally tighten shared helpers without checking historical access and staff dependencies. Do not apply shared/live migrations as a way to discover compatibility. Authenticated acceptance is **not yet the only major gate**.
